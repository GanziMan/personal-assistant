# 설계 결정 기록 (ADR)

결정한 것과, 그때 버린 선택지를 남긴다. 나중에 "왜 이렇게 했지"에
답하기 위한 문서다.

---

## ADR-001 — 클라우드 모델 중심, 로컬은 보조

**결정.** 판단·계획·코딩은 Claude API로 보내고, 임베딩·분류·짧은 요약만
로컬 모델이 맡는다.

**버린 것.** 완전 로컬 구성. 프라이버시는 최상이지만, 선택한 용도 네 가지
중 개발 보조와 다단계 도구 사용에서 로컬 모델(7~30B)의 품질이 확실히
무너진다. 매일 쓰지 않을 비서를 완벽하게 만드는 것은 의미가 없다.

**대비책.** 라우터를 단일 경유지로 두어, 나중에 로컬 모델이 충분히
좋아지면 정책 테이블만 바꿔 비중을 옮길 수 있게 한다.

---

## ADR-002 — 전용 벡터DB 대신 SQLite + sqlite-vec

**결정.** 기억 저장소는 SQLite 파일 하나. 벡터 검색은 sqlite-vec 확장.

**버린 것.** Chroma, Qdrant, LanceDB. 전부 별도 프로세스나 서버를
요구하고, 상주형 개인 비서에 상시 떠 있어야 할 부품을 하나 더 늘린다.
개인 규모(수십만 청크)에서 성능 이득이 그 복잡도를 정당화하지 못한다.

**대비책.** 저장소 접근은 리포지터리 인터페이스 뒤에 둔다. 규모가
커지면 구현만 교체한다.

---

## ADR-003 — 포트가 아니라 유닉스 소켓

**결정.** SwiftUI 앱과 데몬은 `~/.assistant/agent.sock` 로 통신한다.

**버린 것.** localhost HTTP 서버. 같은 맥의 다른 프로세스나 브라우저
페이지가 비서에게 말을 걸 수 있게 된다. 비서는 캘린더·파일·개발 레포에
손이 닿는 존재라 그 표면을 열어둘 이유가 없다.

---

## ADR-004 — UI는 두뇌를 갖지 않는다

**결정.** SwiftUI 앱에는 모델 호출도 도구 실행도 두지 않는다. 입력 전달과
스트리밍 렌더링만 한다.

**이유.** UI는 가장 자주 갈아엎게 되는 층이다. 터미널 CLI, 메뉴바 앱,
나중에 iOS 앱까지 붙이더라도 두뇌는 하나면 된다.

---

## ADR-005 — 자동 실행보다 확인 게이트

**결정.** 파일 삭제·덮어쓰기·외부 전송은 사용자 확인을 거친다.
파일 정리 같은 선제 작업도 실행이 아니라 제안으로 올린다.

**이유.** 비서가 신뢰를 잃는 경로는 못 알아듣는 것이 아니라, 알아들은
척하고 뭔가를 지우는 것이다. 신뢰를 쌓은 다음 화이트리스트로 하나씩
자동화를 푼다.

---

## ADR-006 — 런타임을 레포 밖(~/.assistant)에 둔다

**결정.** 가상환경과 데이터를 `~/.assistant` 아래에 만들고, 패키지는
editable 이 아닌 일반 설치로 넣는다. 레포에는 소스만 남는다.

**이유.** macOS 의 TCC 가 `~/Documents`, `~/Desktop`, `~/Downloads` 를
보호한다. Terminal 에서 실행할 때는 Terminal 에 부여된 권한을 빌려 쓰지만,
launchd 로 뜬 데몬에는 그 권한이 없다. 레포가 `~/Documents` 에 있으면
데몬이 자기 venv 의 `pyvenv.cfg` 조차 읽지 못하고 기동 즉시 죽는다.

    PermissionError: [Errno 1] Operation not permitted:
      '/Users/…/Documents/personal-assistant/core/.venv/pyvenv.cfg'

**버린 것.** 데몬 바이너리에 전체 디스크 접근 권한을 주는 방법. 설치
과정에 수동 단계가 들어가고, 비서에게 필요 이상의 권한을 영구히 주게 된다.

**대가.** editable 설치가 아니라서 코드를 고치면 `install.sh` 를 다시
실행해야 한다. 개발 중에는 번거롭지만, 설치가 조용히 실패하는 것보다 낫다.

## ADR-007 — 구독(Claude Agent SDK)을 기본 두뇌로

**결정.** 기본 백엔드를 Claude Agent SDK 로 바꾼다. Claude Code 로그인
자격으로 동작하고 사용량은 Pro/Max 구독 한도에서 빠진다. Messages API
직접 호출(API 키, 토큰 과금)은 `backend = "api"` 로 남겨둔다.

**이유.** 구독을 이미 쓰고 있는데 API 로 또 내는 것은 같은 것을 두 번
사는 일이다. Agent SDK 와 `claude -p` 는 구독 한도에서 차감되며, 개인
자동화는 허용 범위다. (팀 공용 프로덕션 자동화는 API 를 쓰라는 것이
Anthropic 의 안내다.)

**대가.** 에이전트 루프와 MCP 연결을 SDK 가 가져간다. 우리 쪽 도구
레지스트리는 규칙 잡 경로에서만 쓰이고, 확인 게이트는 SDK 경로에서
아직 붙지 못했다 — 그때까지는 되돌릴 수 없는 도구를 모델에 노출하지
않는 쪽으로 막아둔다. 구독 한도를 데몬이 갉아먹으므로, 자동 잡이
사용자 본인의 작업 한도를 잠식하지 않게 유지하는 것이 중요해진다.

## ADR-008 — 자주 도는 잡은 모델을 쓰지 않는다

**결정.** 잡에 `mode` 를 둔다. `agent` 는 모델을 부르고, `rule` 은
파이썬 함수가 도구만 불러 문자열을 돌려준다. 하루 24회를 넘게 도는
잡은 규칙이어야 한다 (테스트로 강제).

**이유.** "30분 안에 시작하는 일정이 있으면 알려줘"는 판단이 필요 없다.
캘린더를 읽고 시간을 빼면 끝난다. 이걸 15분마다 에이전트에 태우면
하루 96번 모델을 부르게 되고, 비용(또는 구독 한도)의 대부분이 여기서
나온다. 실제 계산으로 월 10만원 규모였다.

**일반화.** 모델은 판단이 필요할 때만 부른다. 조회·산술·임계값 비교는
코드가 할 일이다. 에이전트로 만들 수 있다는 것이 에이전트로 만들
이유가 되지는 않는다.

## ADR-009 — 메뉴바 앱은 Xcode 프로젝트를 두지 않는다

**결정.** SwiftPM 패키지로 빌드하고, `.app` 번들은 `scripts/build-app.sh`
가 조립한다.

**이유.** 두 가지다. `.xcodeproj` 는 diff 가 읽히지 않아 레포에 두면
변경 리뷰가 불가능해진다. 그리고 SwiftPM 은 Command Line Tools 만으로
빌드돼서, 전체 Xcode(수 GB) 설치를 요구하지 않는다.

**대가.** Info.plist 와 번들 구조를 손으로 관리한다. 메뉴바 앱 하나
수준에서는 스크립트 40줄이면 끝난다.

## ADR-010 — 전역 단축키에 Carbon 을 쓴다

**결정.** ⌥Space 를 `RegisterEventHotKey`(Carbon) 로 잡는다.
`NSEvent.addGlobalMonitorForEvents` 를 쓰지 않는다.

**이유.** NSEvent 전역 모니터는 손쉬운 사용(Accessibility) 권한을
요구한다. 그 권한은 키보드 입력 전체를 들여다볼 수 있게 해준다.
비서를 단축키로 부르자고 내줄 권한이 아니다. Carbon API 는 오래됐지만
해당 단축키 조합만 받고 권한을 요구하지 않는다.

## ADR-011 — SDK 백엔드를 사용자 Claude Code 설정에서 격리한다

**결정.** `strict_mcp_config=True` 와 `setting_sources=[]` 를 준다.
비서는 우리가 붙인 MCP 서버만 쓰고, 사용자의 CLAUDE.md·프로젝트
설정·전역 커넥터를 읽지 않는다.

**이유.** 기본값으로 두면 비서가 사용자의 Claude Code 환경을 통째로
물려받는다. 실제로 첫 실행에서 Google Calendar 커넥터와 TodoMate 를
잡고 "인증해 달라"고 요구했다. 비서가 어떤 도구에 손이 닿는지는
이 레포의 설정만으로 결정되어야 한다 — 사용자가 다른 작업을 하려고
붙인 커넥터가 비서의 권한이 되어서는 안 된다.

**곁가지.** MCP 서버 명령을 절대 경로로 준다. SDK 가 띄우는 자식
프로세스의 PATH 에는 `~/.assistant/venv/bin` 이 없어서, 이름만 주면
'실행 파일을 찾지 못함' 으로 조용히 실패한다.

## ADR-012 — 확인 게이트를 can_use_tool 로 구현한다

**결정.** 되돌릴 수 없는 도구는 SDK 의 `can_use_tool` 에서 거부하고,
사용자가 `/승인` 을 보내면 그 도구 한 번만 풀어준 뒤 원래 요청을
다시 보낸다.

**승인은 1회용이다.** 한 번 허락한 삭제가 세션 내내 유효하면 게이트가
아니다. 다른 도구로 새지도 않는다 — 둘 다 테스트로 고정했다.

**대가.** 승인하면 요청이 처음부터 다시 돈다. 모델을 한 번 더 부르는
셈이지만, 파괴적 작업은 드물게 일어나므로 감수한다.

## ADR-013 — 파일 서버에 삭제 도구를 두지 않는다

**결정.** 파일 MCP 서버는 조회·검색·읽기·중복 탐지·정리 제안과
`move_file` 만 노출한다. 삭제 도구는 만들지 않는다.

**이유.** 되돌릴 수 없는 작업 중에서도 파일 삭제는 실수의 대가가
가장 크고, macOS 에서 프로그램이 지운 파일은 휴지통에도 가지 않는다.
그리고 정리라는 목적은 '옮기기' 로 전부 달성된다 — 하위 폴더로
모아두면 사용자가 Finder 에서 확인하고 지우면 된다.

`find_duplicates` 도 묶어서 보여주기만 하고 지우지 않는다. 비서가
"이건 중복이니까 지웠습니다" 라고 말하는 순간, 그 판단이 한 번이라도
틀리면 신뢰가 끝난다.

**경계.** 허용 루트 밖은 해석 후 검사로 막는다. `..` 와 심볼릭
링크로 빠져나가는 경로를 문자열 검사로는 못 막기 때문이다. 루트
안이라도 `.ssh`, `.git`, `Library` 등은 이름으로 차단한다.

## ADR-014 — 웹 검색·페치는 내장 도구를 쓴다

**결정.** Claude Code 내장 `WebSearch` / `WebFetch` 를 허용 목록에
넣는다. 직접 만들지 않는다.

**이유.** 검색 API 는 키와 과금이 따라오고, HTML 본문 추출은 계속
깨지는 종류의 코드다. 이미 잘 도는 것을 다시 만들 이유가 없다.

**여전히 막는 것.** `Read`, `Write`, `Bash` 같은 내장 도구는 주지
않는다. 그것들은 파일 서버의 경로 경계를 그대로 우회한다 — 경계를
한 곳에 두려면 파일 접근은 우리 서버만 통해야 한다.

**피드는 직접 만든다.** RSS 는 구독 목록이라는 상태를 갖고, 아침
브리핑이 매일 같은 출처를 읽어야 한다. 내장 검색으로는 대체되지 않는다.
파싱은 표준 라이브러리로 한다 — 필요한 건 제목·링크·시각 세 개뿐이고,
깨진 XML 이 흔해서 실패를 우리가 제어할 수 있어야 한다.

## ADR-015 — 의존성에 상한을 건다

**결정.** 모든 의존성을 `>=x,<y` 로 적는다. `mcp>=1.2` 처럼 상한
없이 열어두지 않는다.

**계기.** MCP SDK 가 2.0 으로 올라가면서 `FastMCP` 가 `MCPServer` 로
바뀌었고, 재설치 한 번에 MCP 서버 네 개가 전부 죽었다. 데몬 로그에는
`Connection closed` 만 남아서, 원인이 우리 코드인지 환경인지 구분되지
않았다.

**함께 얻은 것.** 이 사고로 통합 테스트를 만들었다
(`test_registry_integration.py`). 실제로 서버 프로세스를 띄우고 도구
목록을 받아온다. 단위 테스트 117건이 전부 통과하는 상태에서도
프로토콜이 어긋나면 런타임에만 드러난다 — 실제로 이 테스트가
`Tool.inputSchema → input_schema`, `isError → is_error` 를 잡아냈다.

## ADR-016 — 개발 서버는 읽기 전용이고 명령을 실행하지 않는다

**결정.** dev 서버는 조회만 한다. `git commit`·`push`·`checkout`
같은 상태 변경 명령도, 테스트나 빌드 실행도 넣지 않는다.

**이유.** 테스트 실행은 곧 레포 안의 임의 코드 실행이다. 파일 서버에
경로 경계를 세우고 파괴적 도구에 확인 게이트를 붙여놨는데, `pytest`
하나를 허용하면 그 전부가 무의미해진다 — conftest.py 는 무엇이든 할
수 있다.

git 쓰기도 마찬가지다. 비서가 커밋을 만들면 그 판단이 틀렸을 때
사용자가 이력을 되돌려야 한다. 레포 안에서 실제로 작업하는 일은
Claude Code 가 이미 더 잘한다.

**그래서 남는 쓸모.** 여러 레포를 가로지르는 시야다. "손 놓은 브랜치
있어?", "어제 뭐 했지", 금요일 회고에 붙는 커밋 요약 — 한 레포 안에
들어가 있을 때는 보이지 않는 것들이다.

**탐색은 자동으로.** 레포 경로를 묻지 않고 흔한 위치를 훑는다.
설정을 하나 줄이는 쪽이 실제로 쓰이게 만든다.

## ADR-017 — 상시 패널은 NSPanel, 대기 화면은 모델을 부르지 않는다

**결정.** 메뉴바 팝오버 대신 항상 떠 있는 `NSPanel` 을 쓴다.
`nonactivatingPanel` 로 만들어, 패널을 눌러도 앞 앱의 포커스를
빼앗지 않는다.

**이유.** 코드를 보다가 비서에 한 줄 묻는 흐름에서, 편집기 포커스가
매번 날아가면 못 쓴다. 일반 NSWindow 는 이걸 피할 방법이 없다.

**대기 화면.** 항상 떠 있는 창이 비어 있으면 거슬려서 닫게 되고,
가득 차면 작업에 방해가 된다. 다음 일정 카운트다운, 남은 할 일,
접어둔 아침 브리핑만 둔다.

**대기 화면은 모델을 부르지 않는다.** 1분마다 갱신되는 화면이 매번
모델을 부르면 하루 1440번이다 — 15분 잡에서 겪은 것과 같은 실수를
UI 쪽에서 반복하는 셈이다 (ADR-008). 데몬에 STATUS 요청을 두고,
도구만 직접 불러 45초 캐시로 돌려준다. 갱신 주기도 상황에 맞춘다 —
일정이 임박하면 20초, 아무 일 없으면 2분.

## ADR-018 — 체감 속도는 네 군데에서 나왔다

**증상.** 답변이 오래 걸린다는 불만. 측정해보니 원인이 하나가 아니었다.

**1. 문장 단위 스트리밍.** SDK 기본값은 완성된 메시지를 통째로 준다.
실제 지연이 같아도 "아무 일 없다가 한 번에 쏟아지는" 것은 훨씬 느리게
느껴진다. `include_partial_messages=True` 로 토큰 단위 델타를 받는다.
체감 개선의 대부분이 여기다.

**2. 추론 강도.** 기본값이 high 다. 비서가 하는 일은 대부분 조회와
요약이라 그 강도가 필요 없다. `effort="low"` 로 내린다. 판단이 필요한
작업에서 품질이 떨어지면 config 로 올린다.

**3. 첫 질문이 기동 비용을 치렀다.** SDK 는 첫 연결에서 claude
프로세스와 MCP 서버들을 전부 띄운다. 데몬 기동 시 미리 연결해두고,
앱은 고정 세션("panel")을 써서 그 예열을 재사용한다.

**4. MCP 서버를 두 벌 띄우고 있었다.** SDK 가 5개를 띄우는데 우리
레지스트리가 또 5개를 띄워 총 10개였다. 데몬이 직접 부르는 것은
대기 화면(calendar)과 알림(system)뿐이라, 구독 백엔드일 때는 그
둘만 띄운다.

**원칙.** 체감 지연은 총 소요 시간이 아니라 '첫 글자까지의 시간'과
'진행이 보이는가'로 결정된다. 최적화는 그 둘부터 본다.

---

## ADR-019 — 아바타는 캐릭터가 아니라 빛덩어리

**결정.** 비서의 시각적 존재를 추상적인 발광 원으로 만든다. 얼굴이나
캐릭터를 넣지 않는다. 상태에 따라 숨쉬기(대기)·회전 맥동(생각 중)·
주황 경고(임박)로 달라진다.

**이유.** 맥에 하루 종일 떠 있는 도구가 귀여운 얼굴을 하고 있으면
하루 이틀은 즐겁고 그다음부터 거슬린다. 존재감은 주되 성격은 주지
않는 선이 상시 상주물에 맞다.

**접근성.** `accessibilityReduceMotion` 이 켜져 있으면 애니메이션을
돌리지 않는다. 움직임에 민감한 사람에게 상시 떠 있는 맥동은 고문이다.

---

## ADR-020 — 인사말과 제안 칩도 규칙으로 만든다

**결정.** 대기 화면 상단의 한 줄과 입력창 위 제안 버튼은 클라이언트에서
규칙으로 계산한다. 모델을 부르지 않는다.

**이유.** 화면이 갱신될 때마다 호출이 나가는 구조는 이 프로젝트에서
이미 두 번 문제가 됐다 (ADR-008, ADR-017). "곧 시작합니다" 나 "좋은
아침입니다" 는 시각과 남은 분으로 결정되는 것이지 추론이 아니다.

**제안 칩의 역할.** 비서에게 뭘 시킬 수 있는지 매번 떠올리지 않아도
되게 한다. 상황에 따라 달라진다 — 아침엔 브리핑, 금요일 오후엔 회고,
일정이 있으면 회의 준비.

---

## ADR-021 — 마크다운은 직접 나눈다

**결정.** 답변 본문을 문단·목록·코드 블록 셋으로만 나눠 그린다.
마크다운 라이브러리를 끌어오지 않는다. 인라인 서식(굵게, 기울임,
인라인 코드, 링크)은 표준 `AttributedString(markdown:)` 이 처리한다.

**이유.** 비서 답변에 나오는 구조는 사실상 이 셋뿐이다. 표와 각주까지
지원하는 라이브러리는 여기서 쓸 일이 없고, 상주 앱의 바이너리와
의존성만 늘린다.

**계기.** 답변이 전부 민무늬 텍스트로 나와 `**굵게**` 가 그대로
보였다. 읽히는 정도에서 차이가 가장 컸던 항목이다.

## ADR-022 — 색을 직접 쓰지 않고 Theme 을 거친다

**결정.** 테두리·카드 배경은 `Theme.stroke(scheme)` 처럼 색 구성을
받아 결정한다.

**계기.** 테두리를 `.white.opacity(0.07)` 로 줬더니 다크 모드에서는
은은한 경계였지만 라이트 모드에서는 흰 배경에 흰 선이라 아무것도
보이지 않았다. 다크만 보고 만든 탓이다.

**부수 효과.** 진행 표시도 같은 원칙으로 정리했다 — 도구 칩은 도는
동안 스피너, 끝나면 체크. 첫 글자 전에는 점 세 개가 움직인다.
빈 줄만 있으면 멈춘 것처럼 보인다.

---

## ADR-023 — 패널 대화는 데몬 기억과 따로 저장한다

**결정.** 패널에 보이는 대화는 `~/.assistant/panel-conversation.json`
에 최근 60줄만 남긴다. 데몬의 SQLite 기억과 섞지 않는다.

**이유.** 둘은 목적이 다르다. 기억은 "무엇이 있었나"를 쌓아 나중에
검색하는 곳이고, 이 파일은 앱을 껐다 켰을 때 화면을 복원하는 용도다.
화면 복원을 위해 기억 DB 를 뒤지기 시작하면 두 관심사가 엉킨다.

**도구 줄은 복원하지 않는다.** 이미 끝난 호출을 다시 보여줄 이유가
없고, 복원된 스피너는 거짓말이 된다.

---

## ADR-024 — 접힌 모드는 창을 숨기는 대신 줄인다

**결정.** ⌘J 로 패널을 높이 76pt 짜리 바로 접는다. 접힌 상태에서는
제목 자리에 다음 일정 카운트다운이 올라온다.

**이유.** 집중해서 작업할 때 패널 전체는 방해가 되지만, 완전히 닫으면
다음 일정을 놓친다. 접힌 바는 그 사이를 메운다.

**위쪽 모서리를 고정한다.** 높이만 줄이면 창이 화면에서 튀어 오르는
것처럼 보인다. maxY 를 유지한 채 origin 을 다시 계산한다.

## ADR-025 — 감지보다 어려운 것은 반복하지 않는 것

**결정.** 감지 신호마다 키·쿨다운·상태 지문을 둔다. 같은 키는 쿨다운
안에 다시 말하지 않고, 지문이 달라졌을 때만 쿨다운을 무시한다.

**이유.** "다운로드가 지저분합니다" 를 30분마다 듣는 비서는 꺼진다.
선제적으로 말하는 기능의 성패는 감지 정확도가 아니라 침묵의 규율에서
갈린다.

**지문의 역할.** 디스크 95% → 97% 는 새 소식이고, 95% → 95% 는
아니다. 파일 41개 → 42개도 새 소식이 아니라서 10개 단위로 뭉뚱그린다.

**해소되면 잊는다.** 조건이 풀리면 기록을 지워서, 다시 생겼을 때
쿨다운을 기다리지 않게 한다.

**세 단계로 나눈다.** QUIET 는 기억에만, NOTE 는 패널 쪽지로, ALERT 만
시스템 알림을 띄운다. 쪽지는 24시간 뒤 스스로 사라진다 — 사용자가
치우지 않아도 쌓이지 않아야 한다.

---

## ADR-026 — 접기는 애니메이션하지 않는다

**결정.** 컴팩트 전환에서 창 크기 애니메이션과 SwiftUI 내용
애니메이션을 모두 끈다. 즉시 바뀐다.

**계기.** 접을 때 레이아웃이 어긋나 보였다. 원인이 둘이었다.

1. 컴팩트 높이를 76pt 로 잡았는데 헤더 실제 높이는 64pt 였다.
   남는 12pt 가 아래 빈칸으로 남아 헤더가 위로 쏠려 보였다.
   이제 헤더가 컴팩트 높이를 직접 채우고 세로 중앙에 놓인다.

2. 창 크기는 AppKit 이, 내용은 SwiftUI 가 각자 다른 커브와 길이로
   움직였다. 두 애니메이션이 겹치는 중간 프레임에서 내용이 창보다
   크거나 작아 보였다.

**판단.** 두 레이어를 프레임 단위로 맞추는 방법은 있지만, 상시
떠 있는 패널에서 0.2초 애니메이션을 위해 감수할 복잡도가 아니다.
즉시 전환이 오히려 깔끔하다.

**곁가지.** 접힌 동안에는 세로 리사이즈를 막는다 (minSize = maxSize).
늘려봐야 빈칸만 생긴다.

---

## ADR-027 — 업무 로그는 모델 없이 쌓고, 읽을 때만 모델이 본다

**결정.** 매일 18:30 에 커밋·일정·완료한 할 일을 모아 `worklog`
분류로 기억에 쌓는다. 이 적재에는 모델을 쓰지 않는다.

**이유.** "오늘 무엇을 했는가"는 조회와 정리의 문제다. 추론이 아니다.
요약이 필요한 것은 사용자가 "이번 분기 뭐 했지" 라고 물을 때이고,
그때 모델이 쌓인 로그를 읽으면 된다. 매일 요약을 만들어두면 매일
모델을 부르면서 정작 필요할 때는 원본이 없다.

**열람은 검색이 아니다.** 업무 로그는 질의어로 찾는 게 아니라 기간으로
훑는 것이 맞다. `episodes_by_kind(kind, since)` 를 따로 뒀다.

**기억 서버는 읽기 전용이다.** 모델이 기억을 직접 고쳐 쓰기 시작하면
무엇이 사실인지 추적할 수 없게 된다. 쌓는 일은 스케줄러와 에이전트
루프가 한다.

---

## ADR-028 — 회의 준비는 모으기만 하고 요약하지 않는다

**결정.** 일정 15분 전에 같은 제목의 지난 기록, 제목과 겹치는 파일,
작업 중인 레포를 모아 패널 쪽지로 올린다. 모델을 부르지 않는다.

**이유.** 모으는 일은 전부 조회다. 5분마다 도는 잡에서 모델을 부르면
하루 288번이 된다 (ADR-008). 쪽지를 보고 더 알고 싶으면 사용자가
패널에서 묻고, 그때 모델이 읽는다.

**흔한 제목은 검색하지 않는다.** "주간 회의" 로 기억과 파일을 뒤지면
관계없는 것이 잔뜩 나와서 준비가 오히려 방해가 된다. 불용어를 걸러
남는 말이 없으면 파일·기록 검색을 건너뛴다.

**일정이 지나면 쪽지를 치운다.** 끝난 회의 준비가 화면에 남아 있으면
다음 회의 준비와 섞인다.

---

## ADR-029 — 클립보드 이력은 메모리에만, 비밀은 아예 담지 않는다

**결정.** 복사 이력을 MCP 서버 프로세스 메모리에 최대 12개만 둔다.
디스크에 쓰지 않는다. 데몬이 죽으면 함께 사라진다.

**이유.** 클립보드는 비밀번호와 토큰이 지나가는 통로다. 편의를 위해
이력을 남기는 기능이 그대로 자격증명 보관소가 되면 안 된다.

**세 겹으로 막는다.**

1. 비밀번호 관리자가 `org.nspasteboard.ConcealedType` 으로 표시한
   항목은 읽지도 않는다.
2. 토큰·개인키·JWT·`password:` 같은 꼴은 정규식으로 걸러 담지 않는다.
   완벽한 판별은 불가능하므로 과하게 거르는 쪽을 택한다 — 복사 기록
   하나 빠지는 손해는 작고, 토큰이 남는 손해는 크다.
3. 디스크에 쓰지 않으므로 백업·동기화에 섞이지 않는다.

**감시 프로세스를 두지 않는다.** 클립보드를 초 단위로 폴링하면
사용자가 복사하는 모든 것을 상시 감시하게 된다. 비서가 클립보드를
읽는 순간에만 담는다 — 사용자가 물어봤을 때다.

---

## ADR-030 — 문서 색인은 기억과 분리하고, 임베딩은 로컬로만

**결정.** 문서 색인을 `~/.assistant/docindex.db` 에 따로 둔다.
기억 DB 와 섞지 않는다. 임베딩은 Ollama 로컬 모델로만 만든다.

**이유.** 둘은 성격이 다르다. 기억은 사용자와 비서 사이에 있었던
일이라 지우면 복구할 수 없다. 색인은 디스크에 이미 있는 파일의
파생물이라 언제든 지우고 다시 만들 수 있다. 백업 정책도, 삭제
기준도 달라야 한다.

**임베딩을 밖으로 보내지 않는 것이 이 기능의 존재 이유다.** 개인
문서를 통째로 외부 API 에 보내야 한다면 로컬 검색을 만들 이유가
없다. Ollama 가 없으면 벡터 없이 색인하고 키워드 검색만 쓴다 —
품질은 떨어지되 동작은 한다.

**변경 감지는 (크기, mtime) 으로 한다.** 내용 해시를 매번 뜨면
수천 개 파일에서 색인이 느려지고, 이 두 값이 같은데 내용만 다른
경우는 실질적으로 없다.

**청크에 겹침을 둔다.** 문단 경계에 걸친 문장이 양쪽 어디서도
검색되지 않는 일을 막는다. 문서 하나를 통째로 임베딩하지 않는
이유도 같다 — 20페이지의 평균 벡터는 무엇과도 어중간하게 닮는다.

## ADR-031 — 비서는 자기 상태를 드러낸다

**결정.** 패널이 꺼진 기능을 표시한다. 헤더에 노란 점, 대기 화면에
접히는 배너, 펼치면 무엇이 나빠지는지와 고치는 명령이 나온다.
명령은 눌러서 복사한다.

**계기.** Ollama 가 꺼지면 문서·기억 검색이 키워드만 쓰게 되는데,
화면에는 아무 표시가 없었다. 사용자는 "왜 검색이 시원찮지" 를 혼자
추측하게 된다. 조용한 성능 저하는 좋은 침묵이 아니다.

**무엇이 나빠지는지까지 말한다.** "Ollama 꺼짐" 만으로는 고칠지
말지 판단할 수 없다. "문서·기억 검색이 키워드만 씁니다" 까지 있어야
사용자가 지금 켤 일인지 나중에 할 일인지 정한다.

**모든 기능이 정상이면 아무것도 보이지 않는다.** 상태 표시가 늘
떠 있으면 그것도 소음이다.

**여기서도 모델을 부르지 않는다.** 자기 상태는 조회로 알 수 있다.

---

## ADR-032 — 고장 표시는 대기 화면 밖에 둔다

**계기.** Ollama 를 껐는데 패널에 아무 표시가 없었다. 원인이 둘이었다.

1. 배너를 대기 화면 안에 넣어놨는데, 대화가 남아 있으면 대기 화면이
   접힌다. 대화는 디스크에 저장되므로(ADR-023) 앱을 다시 켜도 남아
   있고, 그래서 배너가 영영 보이지 않았다.
2. 상태 캐시 45초 + 폴링 주기 최대 120초라 최악의 경우 3분 가까이
   걸렸다.

**결정.** 배너를 대기 화면 밖으로 옮긴다. 고장은 대화 중에도 보여야
한다. 캐시를 15초로 줄이고, 꺼진 기능이 있으면 폴링을 20초로 당긴다 —
복구도 빨리 알아채야 한다. 패널을 열 때는 즉시 한 번 갱신한다.

**일반화.** "특정 화면에서만 보이는 경고" 는 그 화면에 안 들어가는
사용자에게는 없는 것과 같다. 상태는 항상 같은 자리에 있어야 한다.

## ADR-033 — 맥마다 독립적으로 둔다

**결정.** 여러 맥에서 쓸 때 각 맥에 비서를 따로 설치한다. 설정과
구독 피드만 옮기고, 기억 DB·문서 색인·감지 기록은 옮기지 않는다.

**이유 1 — 내용이 그 맥에 묶여 있다.** 업무 로그는 그 맥의 레포를
훑어 만든 것이고, 문서 색인은 그 맥의 파일 경로를 가리킨다. 회사
맥의 색인을 개인 맥으로 옮기면 존재하지 않는 경로가 잔뜩 남는다.

**이유 2 — SQLite 는 파일 동기화로 나르면 깨진다.** WAL 모드에서
데이터는 `.db`, `.db-wal`, `.db-shm` 세 파일에 나뉘어 있고, iCloud 나
Dropbox 는 이들을 원자적으로 다루지 못한다. 두 맥이 동시에 켜져
있으면 특히 위험하다.

**대신 설치를 한 줄로 만든다.** `bootstrap.sh` 가 의존성·툴체인·
로그인·모델·데몬·앱을 순서대로 확인하고 없는 것만 설치한다.

**가져오기는 되돌릴 수 있어야 한다.** `profile.sh import` 는 덮어쓰기
전에 기존 파일을 백업하고, 피드는 덮어쓰지 않고 합친다.

## ADR-034 — 스크린샷은 OCR 로 읽는다

**결정.** 이미지를 모델에 넘기지 않고 macOS Vision 으로 로컬에서
글자를 뽑아 텍스트로 전달한다.

**이유 1 — 이미지가 맥을 벗어나지 않는다.** 에러 화면에는 보통
경로·호스트명·토큰 조각이 함께 찍혀 있다.

**이유 2 — 에러 메시지라면 OCR 이 더 정확하다.** 고정폭 글꼴의
스택 트레이스는 텍스트로 뽑는 편이 낫다.

**이유 3 — SDK 에 이미지 블록이 없다.** 현재 Agent SDK 의 콘텐츠
타입은 텍스트·도구뿐이다.

**경계.** OCR 대상은 파일 서버의 허용 폴더, 또는 비서가 만든
붙여넣기 폴더뿐이다. 임의 경로의 이미지를 읽어주는 도구가 되면
파일 서버에 세운 경계가 무의미해진다. 붙여넣은 이미지는 24시간 뒤
스스로 지워진다 — 쌓인 스크린샷도 유출 표면이다.

## ADR-035 — 앱은 파일 내용을 읽지 않는다

**결정.** 드래그 앤 드롭과 붙여넣기에서 앱은 경로만 만들어 입력창에
넣는다. 파일을 여는 것은 도구가 한다.

**이유.** 앱이 파일을 직접 읽기 시작하면 경로 경계가 두 곳이 된다.
한쪽만 고치면 구멍이 남는다. 경계는 파일 서버 한 곳에 있어야 한다.

**바로 보내지 않는다.** 떨어뜨리면 입력창에 문장이 채워질 뿐,
전송은 사용자가 한다. 무엇을 시킬지 손볼 여지를 남긴다.

## ADR-036 — 알림은 앱이 띄운다

**결정.** 감지 신호의 알림을 데몬이 아니라 메뉴바 앱이 띄운다.
데몬은 쪽지판에 올려두고, 앱이 그것을 가져가 시스템 알림으로 만든다.

**이유.** 데몬이 osascript 로 띄운 알림은 눌러도 아무 일이 일어나지
않는다. 누를 수 없는 알림은 정보를 반만 준다 — 보고 나서 결국
패널을 직접 열어야 한다.

**중복을 막는다.** 앱은 이미 띄운 쪽지를 기억하고, 쪽지가 사라지면
기록에서도 지운다. 다시 생기면 다시 알린다.

**메뉴바 아이콘도 상태를 말한다.** 기능이 꺼졌으면 sparkle.slash,
일정이 임박했으면 시계, 쪽지가 있으면 돋보기. 패널을 열지 않아도
보인다.

## ADR-037 — 크기와 여백은 토큰에서만 고른다

**결정.** 글자 크기 다섯 단계, 여백 다섯 단계, 모서리 세 단계를
`Theme` 에 정의하고 그 안에서만 고른다. 뷰에 숫자를 직접 적지 않는다.

**계기.** 패널을 다시 보니 글자 크기가 10, 11, 12, 13, 26 으로
섞여 있고 여백이 9, 11, 12, 14, 15 였다. 그때그때 눈대중으로 정한
값들이라 무엇이 더 중요한지 눈이 구분하지 못했다.

**본문을 13pt 로 잡는다.** AppKit 의 기본 크기다. 시스템 앱과 같은
리듬이 나고, 사용자가 이미 익숙한 밀도다.

**여백은 4의 배수만 쓴다.** 그 사이 값을 허용하면 결국 다시 제각각이
된다.

**강조색은 시스템을 따른다.** 사용자가 시스템 설정에서 고른 색이 곧
취향이다. 상주 앱이 자기 색을 고집할 이유가 없다.

**위계를 카드로 드러낸다.** 다음 일정은 강조 카드(임박하면 테두리가
색을 띤다), 할 일과 쪽지는 보통 카드, 브리핑은 접힌 카드. 전부 같은
회색 상자면 중요도 차이가 보이지 않는다.

**빈 상태를 만든다.** 일정도 할 일도 없을 때 "남은 일정 없음" 한 줄만
남기지 않는다. 상주 앱에서 가장 자주 보게 되는 화면이 그 빈 화면이다.

## ADR-038 — 대기 화면은 완전히 숨기지 않는다

**계기.** 대화를 한 번 하면 대기 화면이 사라졌다. 대화는 디스크에
저장되므로(ADR-023) 앱을 껐다 켜도 남고, 결국 한 번 말을 건 뒤로는
다음 일정을 영영 볼 수 없었다. 실제로 사용자가 "일정 없다는 한 줄만
보인다" 고 알려와 드러났다 — 그 한 줄은 대기 화면이 아니라 지난
대화의 답변이었다.

**결정.** 대화가 있으면 헤더 아래에 요약 한 줄을 남긴다. 다음 일정,
할 일 개수, 쪽지 유무가 들어간다. 누르면 대기 화면 전체가 펼쳐진다.

**같은 실수를 두 번 했다.** 상태 배너도 대기 화면 안에 넣었다가
같은 이유로 안 보였다 (ADR-032). 그때 세운 원칙 — "특정 화면에서만
보이는 것은 그 화면에 안 들어가는 사용자에게는 없는 것과 같다" —
을 대기 화면 자체에는 적용하지 않았다.

**일반화.** 상시 표시되어야 하는 정보는 조건부 렌더링 안에 두지
않는다. 접더라도 흔적은 남긴다.

## ADR-039 — 채용공고는 공식 API 로만 가져온다

**결정.** 사람인 공식 API(`oapi.saramin.co.kr`)만 쓴다. 사람인·
잡코리아·원티드 어느 곳도 크롤링하지 않는다.

**이유.** 잡코리아가 사람인을 상대로 채용공고 크롤링 소송을 걸어
최종 승소했다. 공고를 모아둔 것 자체가 데이터베이스 제작자의 권리로
인정됐다. 개인용이라도 자동 수집은 같은 구조다.

**표기 의무.** 사람인 약관이 "Powered by 취업 사람인" 표기를 요구한다.
응답 끝에 출처를 붙인다.

**다른 두 곳.** 원티드는 파트너 연동용이라 개인 승인 여부가 불확실하고,
잡코리아는 공공기관·학교 우선이라 개인 구직용으로는 어렵다. 승인되면
같은 구조로 붙인다 — 클라이언트만 추가하면 되게 모델과 저장소를
서비스에 묶지 않았다.

**본 공고를 기억한다.** 같은 공고를 매번 새 것처럼 보여주면 이 기능은
금방 쓸모없어진다. id 와 본 시각만 남기고 공고 본문은 저장하지 않는다 —
내용은 사이트에 있고 사본을 들고 있을 이유가 없다.

**하루 두 번만 확인한다.** API 에 일일 한도가 있고, 공고는 분 단위로
바뀌지 않는다. 판단이 없으므로 규칙 잡이다 (ADR-008).
